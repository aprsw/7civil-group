# استقرار روی سرور شبکهٔ داخلی (ویندوز)

هدف: همهٔ کارکنان با **یک آدرس** مثل `http://192.168.1.50/` وارد شوند، سامانه با
روشن‌شدن سرور **خودکار بالا بیاید**، و کسی لازم نباشد چیزی را دستی اجرا کند.

---

## چرا یک پورت؟

در حالت توسعه دو سرور جدا اجرا می‌شود (Vite روی ۵۱۷۳ و PHP روی ۸۰۰۰). در شبکه
این کار اشتباه است: Vite یک سرورِ توسعه است، کند و ناامن، و دو آدرسِ جدا یعنی
دردسر CORS. در استقرار واقعی:

```
فرانت‌اند  →  npm run build  →  frontend/dist/  (فایل‌های ثابت)
                                      ↓
                          Apache روی پورت ۸۰
                             ├── /            →  frontend/dist/
                             ├── /api/…       →  backend/public/index.php
                             └── /uploads/…   →  backend/public/uploads/
```

هر سه روی **یک دامنه و یک پورت** → بدون CORS، بدون Node در زمان اجرا، یک آدرس
برای همه. Node فقط موقع build لازم است.

---

## نصب (یک‌بار، روی سرور)

### ۱) آی‌پی ثابت
در Windows → Network → Adapter → IPv4 یک **IP ثابت** بدهید (مثلاً `192.168.1.50`).
اگر IP از DHCP بگیرد، روزی عوض می‌شود و bookmark همه می‌شکند.

### ۲) مسیرها را تنظیم کنید
پروژه را در `C:\7civil-group` بگذارید (یا مسیر را در فایل‌های زیر عوض کنید):
- `deploy/setup-server.bat` → متغیرهای `XAMPP` و `PROJECT`
- `deploy/apache/7civil.conf` → هر چهار مسیر `C:/7civil-group/...`

### ۳) vhost را به Apache معرفی کنید
در انتهای `C:\xampp\apache\conf\httpd.conf` اضافه کنید:

```apache
Include "C:/7civil-group/deploy/apache/7civil.conf"
```

### ۴) اسکریپت نصب را **با Run as administrator** اجرا کنید

```bat
deploy\setup-server.bat
```

این اسکریپت: فرانت را build می‌کند، دیتابیس و دادهٔ اولیه را می‌سازد، Apache را
به‌صورت **سرویس ویندوز** نصب می‌کند (یعنی با روشن‌شدن سرور خودکار بالا می‌آید،
بدون اینکه کسی login کند) و **پورت ۸۰ را در فایروال باز** می‌کند.

### ۵) تست
- روی خود سرور: <http://localhost/>
- از یک سیستم دیگر: `http://<آی‌پیِ سرور>/`

> اگر از سیستم دیگر باز نشد، تقریباً همیشه **فایروال** است. چک کنید:
> `netsh advfirewall firewall show rule name="7CivilGroup Automation"`

### ۶) کارهای امنیتی بعد از نصب
1. `backend\public\install.php` را **حذف کنید**.
2. در `backend\.env` مقدار `JWT_SECRET` را به یک رشتهٔ تصادفی بلند تغییر دهید.
3. `CORS_ORIGINS` را از `*` به آدرس واقعی سرور تغییر دهید.
4. `APP_DEBUG=false` بماند.
5. رمز کاربران نمونه (`password`) را عوض کنید یا حساب‌های آزمایشی را حذف کنید.

## نام به‌جای آی‌پی (اختیاری)

اگر Active Directory / DNS داخلی دارید، یک رکورد A بسازید تا همه
`http://automation/` را باز کنند. بدون DNS، در فایل `hosts` هر سیستم:

```
192.168.1.50   automation
```

---

## بدون Apache — راه سریع‌تر

اگر فعلاً نمی‌خواهید Apache را تنظیم کنید، یک سرور تک‌پورتِ آماده هست:

```bat
C:\xampp\php\php.exe deploy\serve.php 0.0.0.0 8080
```

آدرس: `http://<آی‌پیِ سرور>:8080/`

> ⚠ این روی **سرور داخلی PHP** اجرا می‌شود که **هم‌زمان فقط یک درخواست** را
> پاسخ می‌دهد. برای چند کاربر تست خوب است، برای یک واحد اداری نه — آنجا از
> Apache استفاده کنید.

برای اجرای خودکارش هنگام بوت، یک Task در **Task Scheduler** بسازید با
trigger روی `At startup` و گزینهٔ `Run whether user is logged on or not`.

---

## به‌روزرسانی بعد از تغییر کد

```bat
deploy\update.bat
```

فرانت را دوباره build می‌کند و سرویس را restart می‌کند. **دادهٔ موجود را پاک
نمی‌کند** — جدول‌های جدید خودکار اضافه می‌شوند.

---

## پشتیبان‌گیری — این را جدی بگیرید

کلِ آرشیو نامه‌ها در یک فایل SQLite است. آن فایل برود، همه‌چیز رفته.

```bat
deploy\backup.bat
```

در **Task Scheduler** روزانه اجرایش کنید و مقصد (`DEST`) را روی یک درایو یا
share دیگر بگذارید. فایل‌های `database.sqlite-wal` و `-shm` هم باید کپی شوند
(اسکریپت این کار را می‌کند) وگرنه آخرین تراکنش‌ها در پشتیبان نیستند.

---

## دربارهٔ SQLite در شبکه

- فایل دیتابیس باید روی **دیسک خود سرور** باشد، نه روی یک network share —
  قفل‌گذاری SQLite روی SMB قابل اتکا نیست.
- حالت **WAL** فعال است و `busy_timeout` روی ۱۰ ثانیه، پس چند کاربر هم‌زمان
  مشکلی ندارند (با ۸ نویسندهٔ موازی تست شده).
- برای ده‌ها کاربرِ پرترافیک یا نیاز به گزارش‌گیری سنگین، به MySQL یا
  SQL Server (۲۰۱۴ به بالا) مهاجرت کنید؛ کد هر دو را پشتیبانی می‌کند.
